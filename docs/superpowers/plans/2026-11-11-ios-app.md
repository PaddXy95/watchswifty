# iOS-App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A native SwiftUI iPhone app with every function of the WatchSwifty web UI, talking only to the existing App API, distributed via a public TestFlight link.

**Architecture:** The server repo gains a library product `WatchSwiftyClient` (types + client generated from the same `openapi.yaml`, growing enums made open via `typeOverrides`). A new repo `watchswifty-ios` holds an XcodeGen project with a thin iOS app target (SwiftUI views) and a local package `WatchSwiftyCore` (stores, auth, networking, testable with `swift test` on macOS). No local database: `@MainActor @Observable` stores hold the generated API types and replace them with each response; an `AppModel.changeVersion` makes other screens reload on their next appearance.

**Tech Stack:** Swift 6, SwiftUI (iOS 26), Observation, Swift Charts, AuthenticationServices, CryptoKit, Security (Keychain), swift-openapi-generator 1.14.4 (server repo), swift-openapi-runtime 1.13.4, swift-openapi-urlsession 1.x, XcodeGen, Swift Testing.

**Spec:** `docs/superpowers/specs/2026-11-10-ios-app-design.md` (server repo). Screen contents follow `2026-11-07-watchswifty-design.md` §5; API semantics `2026-11-08-app-api-design.md`; every request/response shape is in `Sources/WatchSwiftyAPI/openapi.yaml`.

## Global Constraints

- Two repos: server = this repo (branch `beta`); app = new repo at `/Users/patrickmeindl/Documents/Projects/watchswifty-ios` (paths below marked **app:** are relative to it).
- iOS deployment target `26.0`, iPhone only (`TARGETED_DEVICE_FAMILY = 1`); Swift 6 language mode, `SWIFT_STRICT_CONCURRENCY = complete`.
- Bundle ID `dev.patmei.watchswifty`; URL scheme `dev.patmei.watchswifty`; redirect URI exactly `dev.patmei.watchswifty:/auth`.
- App dependencies only: `WatchSwiftyClient` (server repo, `branch: "beta"` until Task 18, then `from:` the release tag), `swift-openapi-runtime` `from: "1.13.4"`, `swift-openapi-urlsession` `from: "1.0.0"`.
- No Core Data, no SwiftData, no other persistence except: token in Keychain; server address + device name in `UserDefaults`; last `ContinueWatching` as JSON in the Caches directory; posters in `URLCache` (memory 50 MB, disk 200 MB).
- Keychain item: service `dev.patmei.watchswifty`, account `device-token`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable. The token never appears in logs, errors or UI.
- `http://` only for private targets: IPv4 `10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `127/8`; IPv6 `fc00::/7`, `::1`; names without a dot, `localhost`, suffixes `.local`, `.lan`, `.home.arpa`, `.internal`. Otherwise German error "Bitte eine https://-Adresse verwenden – sonst wäre die Anmeldung unverschlüsselt." Without a scheme `https://` is assumed. Info.plist: `NSAllowsArbitraryLoads = true`, `NSLocalNetworkUsageDescription`.
- Everything the user sees is German (String Catalog, development language `de`, only `de`); server `message` texts are shown verbatim. Code identifiers and comments English. Commits: English Conventional Commits.
- The app never computes business logic itself (next episode, stats, matching); it shows what the API returns.
- Posters: `https://image.tmdb.org/t/p/w{width}{posterPath}`, width = first of `[92, 154, 185, 342, 500, 780]` ≥ point width × screen scale (else 780).
- Upload limits checked before sending: Netflix 10 MB (`10_485_760` bytes), film list 2 MB (`2_097_152`); German error "Die Datei ist zu groß." (same text as the server's `payloadTooLarge`).
- Tests: Swift Testing. Server: `swift test` green at every commit. App: `swift test --package-path Packages/WatchSwiftyCore` green at every commit, and `xcodebuild -project WatchSwifty.xcodeproj -scheme WatchSwifty -destination 'generic/platform=iOS Simulator' -skipPackagePluginValidation build` succeeds.
- Pushing `beta`, merging to `main` (publishes image + GitHub release) and anything in App Store Connect happen only after the user says so.

## Review Focus

1. Double tap on „Gesehen“ on a Start card (or tap + swipe) → exactly one `markNextEpisode` request, carrying the card's `next.episodeId`. Test: `markNextIgnoresSecondTapWhileInFlight` (Task 9).
2. The token expires mid-session while several screens load at once → one switch to „Bitte erneut verbinden“, server address kept, no stack of alerts. Test: `concurrent401sSignOutOnce` (Task 5).
3. A newer server sends an unknown service or status value → the response still decodes, the app shows „Anderer Dienst“, and editing only the date of such a watch sends the unknown value back unchanged. Tests: `unknownServiceDecodes` (Task 1), `editKeepsUnknownService` (Task 11).
4. A sloppily typed address (spaces, capitals, trailing slash, no scheme, sub-path) or `http://` to a public host → normalized, or rejected with the German message. Test: `serverAddressNormalization` (Task 3).
5. Typing fast in search: an older response arriving after a newer one → ignored, results match the current text. Test: `staleSearchResponseIgnored` (Task 10).

## Phase 3 – Kern

Pattern for every store from here on (do not repeat in tasks): `@MainActor @Observable public final class XStore`, `init(api: any APIProtocol, app: AppModel, …)`; screens call `load()` in `.task` and `reloadIfStale()` in `.onAppear`/on `scenePhase == .active`; `.refreshable { await load() }`; a mutation sets `busy`, ignores further mutations while busy, on success replaces the value from the response and calls `app.didChange()`, on failure keeps the value and sets `actionError: UserFacingError?` (shown as alert); first load shows `.redacted(reason: .placeholder)` content. Every view has a `#Preview` backed by `FakeTransport` fixtures.
